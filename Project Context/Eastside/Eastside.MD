# 2. Core Narrative

## What problem existed before this project

Most AI character apps feel flat because:

* Characters reset emotionally.
* Memory is shallow or unreliable.
* There is no world structure.
* Characters wait passively for the user.
* Multi-character interactions rarely matter.
* UI often feels generic or dashboard-like.
* Relationship progression is either fake, too obvious, or not persistent.
* Character discovery feels like browsing bots instead of entering a living world.

## Why the problem mattered

For character-driven AI, immersion is the product.

If the user does not believe the character has continuity, the experience collapses into a novelty chat. Eastside’s product thesis is that emotional attachment depends on:

# 5. Architecture Breakdown

## High-level architecture summary

Eastside is structured around three layers:

1. **Experience layer**

   * FINDR discovery.
   * Character profiles.
   * Chat threads.
   * Group chats.
   * Location scenes.
   * Spotlight card.
   * Character galleries/posts.

2. **State/data layer**

   * Users.
   * Personas.
   * NPCs.
   * Locations.
   * Threads.
   * Containers.
   * Scenes.
   * Messages.
   * Memories.
   * Media assets.
   * Proactive schedules.
   * Token usage logs.

3. **AI orchestration layer**

   * Builds prompts from character identity, relationship state, location, recent messages, memories, and trigger context.
   * Routes requests to LLM providers.
   * Logs token usage.
   * Stores messages.
   * Creates/updates memory.
   * Schedules proactive follow-ups.

## User flow

1. User logs in.
2. User lands in the city/home experience.
3. User opens FINDR.
4. User browses character cards.
5. Most-messaged/popular character can appear in spotlight.
6. User opens a character profile modal.
7. User adds character to chat.
8. User sends messages.
9. Character responds using personality + memory + relationship state.
10. Relationship progresses invisibly: warming up → interested → attached → devoted.
11. User may create a group chat.
12. Group chat memories can be shared across participating characters.
13. User invites a character to a location.
14. A location-bound scene starts.
15. Scene messages are stored with scene/location context.
16. After scene, character may send follow-up based on personality probability.
17. If user mentions real-life events, character may check in later.
18. If user is inactive, character may message up to twice depending on rules.

## Data flow

User action:

* User sends message.

Frontend:

* Sends message with user/persona/container/thread/scene context.

Backend:

* Auth validates user.
* Finds active container/thread/scene.
* Loads participants.
* Loads NPC state.
* Loads relevant memories.
* Loads prompt template.
* Builds context.
* Calls LLM provider.
* Stores user message.
* Stores NPC response.
* Logs token usage.
* Possibly writes memory candidate.
* Possibly schedules follow-up.

Frontend:

* Displays response.
* Updates chat state.
* Updates relationship/progression UI if exposed.
* Updates media if response includes image.

# 8. Challenges and War Stories

## Main technical challenge: making AI characters persistent

Problem:

* AI responses are stateless by default. Eastside needs continuity across chats, scenes, locations, and characters.

Why difficult:

* Context windows are limited.
* Memory retrieval can be noisy.
* Character personalities must stay consistent.
* Group memory needs audience boundaries.
* Different modes need different prompt scopes.

Likely solution approach:

* Store messages, scenes, memories, locations, and character state.
* Use memory records with importance and embeddings.
* Build prompt templates by mode/channel/location/character.
* Retrieve relevant memories before each response.
* Keep relationship state separate from raw chat history.

What it proves:

* You understand AI product architecture beyond API calls.

Case-study paragraph:

> The hardest technical challenge was designing Eastside so characters could feel continuous across sessions. A normal LLM call has no durable memory, so I modeled the surrounding state explicitly: users, personas, NPCs, threads, scenes, locations, messages, memories, and proactive triggers. This created a system where each response could be generated from structured context rather than a single chat transcript.

Blog-style war story:

> Early AI character prototypes are deceptively easy: send a message, get a response, display it in chat. The problem appears after the fifth or tenth conversation. The character forgets what happened, repeats itself, ignores location, and treats emotional milestones as disposable. Eastside forced me to design the “world around the model.” That meant separating phone threads from scenes, giving memories audience scope, tracking relationship state outside the model, and logging token usage so the system could eventually scale without blindly throwing the entire conversation history into every prompt. The lesson was simple: the LLM is not the product. The state layer around the LLM is the product.

Resume bullet:

* Designed persistent AI character architecture using structured messages, scenes, memories, locations, relationship state, and scoped prompt templates to maintain continuity across conversations.

## Main product/design challenge: premium feel without feature spiral

Problem:

* The product needs to feel beautiful and immersive, but endless UI iteration can delay alpha.

Why difficult:

* Eastside’s value depends heavily on vibe.
* FINDR needs to feel premium, not like a dashboard.
* Animations, images, cards, and modals can become a rabbit hole.

Likely solution:

* Freeze core UI foundation.
* Lock card-to-modal animation.

# 13. Case Study Copy

## Hero headline

**Building an AI visual novel where characters remember, react, and reach out first.**

## Hero subheadline

**Eastside is a full-stack AI character platform set in a fictional city, combining FINDR discovery, persistent memory, proactive messaging, group chats, and location-bound scenes into a premium visual novel experience.**

## Overview paragraph

Eastside is an AI-led freestyle visual novel designed around immersion and continuity. Users enter Easthaven, a fictional city inspired by NYC/DC, and meet characters through FINDR, a dating-app-inspired discovery interface with profile cards, cinematic images, bios, prompts, and spotlight features. From there, users can chat with characters, build relationships, create group conversations, and invite characters into location-based scenes.

## Problem paragraph

Most AI character experiences feel temporary. A user can have a good conversation, but the next interaction often loses emotional continuity. Characters forget important events, wait passively for the user, and rarely feel connected to a broader world. Eastside addresses that gap by treating characters as persistent entities with locations, relationships, memories, personalities, and proactive behavior.

## Solution paragraph

Eastside combines a polished frontend experience with a structured AI backend. Characters are discovered through FINDR, added to chat, progressed through invisible relationship states, and connected to scenes in specific city locations. The system supports proactive messages, group chat memory, important-event follow-ups, and media-backed character profiles. Instead of building a generic chatbot, Eastside builds the surrounding product system that makes AI character interaction feel continuous.

## Technical architecture paragraph

The architecture models Eastside as a persistent world state around AI conversations. The backend stores users, personas, NPCs, locations, threads, scene containers, messages, memories, media assets, proactive schedules, prompt templates, and token usage. AI responses are generated using scoped context: character identity, relationship state, location, participants, recent messages, retrieved memories, and trigger metadata. Background schedules support proactive messages, follow-ups, and inactivity-based check-ins.

## Key features section

* **FINDR discovery:** cinematic character cards, bios, prompts, and profile modals.
* **Dynamic spotlight:** a horizontal 16:9 feature card for the most active or highlighted character.
* **Persistent memory:** characters can remember meaningful user facts, events, and prior scenes.
* **Relationship progression:** invisible emotional gates move characters from warming up to devoted.
* **Group chat memory:** shared conversations can affect multiple characters.
* **Location-bound scenes:** users can invite characters into city locations for contextual interactions.
* **Proactive messaging:** characters can check in after scenes, inactivity, ignored messages, or important events.
* **Media system:** character profiles, galleries, posts, and message images share a reusable asset model.
* **Admin tooling:** roadmap includes character management, image management, message monitoring, and trigger controls.

## Challenge paragraph

The main challenge was designing the system around the AI rather than relying on the AI alone. Eastside needed durable state: who the user is, which persona they are using, which character is speaking, where the scene occurs, what memories matter, which other characters were present, and when a character should initiate contact. That required a backend architecture capable of supporting narrative continuity, not just message generation.

## Outcome paragraph

Eastside is currently positioned as a private alpha project under Vanta Solutions. It demonstrates full-stack AI product development across UI design, database architecture, AI orchestration, memory systems, media management, proactive scheduling, and product roadmap planning. The next milestone is a playable friend alpha with core discovery, chat, character content, memory, images, simple locations, telemetry, and admin controls.

## Lessons learned paragraph

The biggest lesson is that AI product quality comes from the system around the model. Prompting matters, but the product becomes believable through state, memory, retrieval, UI context, background jobs, rate limits, admin tools, and iteration loops. Eastside is a reminder that the “magic” of AI characters is built through careful engineering and product design.

## Future roadmap paragraph

Near-term work focuses on authentication, production deployment, dev dashboard controls, character content, image systems, lightweight posts, a simple city map, memory polishing, telemetry, and friend alpha testing. Post-alpha ideas include richer social feeds, global character media, deeper relationship arcs, interactive maps, advanced memory, and monetization through premium characters or experiences.

## CTA paragraph

Eastside is part of my Vanta Solutions portfolio, showing how I approach AI-native products from concept to architecture, frontend experience, backend systems, and product roadmap execution.
